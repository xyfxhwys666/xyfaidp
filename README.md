# 优探乐享生活

优探乐享生活是一个本地生活探索平台，围绕"发现附近的好店"这一核心场景搭建。用户可以在平台上浏览店铺分类、查看附近商户、阅读其他用户发布的真实探店笔记、关注感兴趣的作者，也可以领取优惠券并参与限时秒杀。

平台最主要的特点是把大模型能力真正接入了日常业务链路，而不是只做一个聊天入口。用户可以直接用自然语言说出自己的需求，系统理解意图后结合地理位置检索店铺，再由模型重排并给出推荐理由；店铺详情页的口碑总结由模型从大量探店笔记中自动提炼；发布笔记时，模型会参与内容质检与风险拦截。为了让模型能力与核心业务互不干扰，平台在架构上把 AI 能力拆成了独立的 Sidecar 服务。

本文档依次介绍整体架构、全部业务模块、AI 能力设计、缓存与可靠性方案、数据库结构，以及完整的本地部署流程。

## 整体架构

平台由三层组成：前端静态页面、主业务服务、AI 服务。

前端是一组静态页面，由 Nginx 托管。Nginx 同时承担反向代理职责，页面发出的接口请求统一带有 /api 前缀，由 Nginx 剥离前缀后转发给主业务服务。前端本身不直接调用任何大模型接口，用户的每一次 AI 操作都经过后端编排。

主业务服务承载全部业务逻辑，技术栈以稳定为优先，使用 Java 8、Spring Boot 2.3.12、MyBatis-Plus，缓存使用 Redis，分布式锁使用 Redisson，秒杀异步下单使用 RabbitMQ。这个服务不直接依赖大模型 SDK，所有模型调用都通过 HTTP 发往 AI 服务。

AI 服务单独承载模型相关能力，使用 Java 17、Spring Boot 3.3.5 和 Spring AI，对主业务服务暴露六个内部接口，分别负责分段摘要、最终摘要、意图解析、推荐理由、推荐重排和内容风控。它可以独立部署、独立升级，模型供应商也可以独立替换。当前接入的是阿里云 DashScope，API 密钥只从环境变量读取，不写入配置文件、不进入代码仓库。

一次完整的请求链路是：用户操作页面，请求到达 Nginx，Nginx 转发到主业务服务，主业务服务完成数据检索、缓存判断、规则过滤后，按需通过 HTTP 调用 AI 服务，AI 服务再调用大模型并把结果返回，最终由主业务服务统一组装后响应给前端。

这样拆分有四个实际好处。第一，主业务服务保持成熟稳定的技术底座，不需要为了模型 SDK 做整体版本升级。第二，AI 服务的迭代节奏完全独立，可以随时调整提示词、升级框架。第三，模型供应商可替换，切换过程不影响主业务代码。第四，模型超时或不可用时，主业务服务和 AI 服务两侧都准备了本地规则兜底，用户侧功能不会直接瘫痪。

## 业务模块

### 用户体系

用户登录采用手机号加短信验证码的方式。用户输入手机号后请求验证码，验证码保存在 Redis 中并设置两分钟有效期；用户提交手机号和验证码后，服务端校验通过即创建或复用用户，生成随机登录令牌存入 Redis，返回给前端并由后续请求携带。

会话管理通过两个拦截器协作完成。刷新令牌的拦截器拦截全部请求，只要请求中带有有效令牌就刷新其有效期，并把用户信息存入线程上下文；登录校验拦截器只作用于需要登录的路径，从线程上下文中判断当前是否为已登录用户。两个拦截器按顺序注册，保证用户在活跃期间会话不过期，同时未登录访问受保护资源时被准确拦截。

除登录之外，用户体系还包含个人主页、详细资料查看，以及每日签到。签到基于 Redis 的 BitMap 实现，每个用户每个月占用一段位图，签到时把对应日期的位标记为 1，连续签到统计则通过 BitField 命令取出整段位图逐位计算。

### 店铺体系

店铺体系包含分类浏览、店铺详情、附近店铺和按名称搜索。

店铺分类列表缓存在 Redis 的有序集合中，以分类的排序值作为分数，页面加载分类导航时优先读缓存，缓存不存在时查数据库并回填，减少数据库访问。

店铺详情是缓存设计最集中的地方。查询店铺时优先读取 Redis 缓存，命中后直接返回；未命中时查询数据库并写入缓存。针对缓存穿透，当数据库中也查不到该店铺时，会把空值对象写入缓存并设置较短有效期，避免恶意请求反复打到数据库。针对缓存击穿，热点店铺的回源使用互斥锁保护，同一时刻只有一个请求能查询数据库并重建缓存，其余请求等待后读取新缓存。缓存本身设置了三十分钟有效期，配合随机过期思路降低大面积同时失效的风险。

附近店铺基于 Redis GEO 实现。每家店铺按类型把坐标写入 GEO 集合，用户查看附近店铺时，服务端直接按经纬度检索指定范围内的店铺并计算距离，再按距离排序、按页返回。当 Redis 中缺少数据时，查询自动降级到数据库兜底，保证功能可用。

### 笔记社区

笔记社区提供探店笔记的发布、详情、点赞、热门榜单和分页浏览。

发布笔记时，请求先经过 AI 风控校验，存在高风险的内容会被拒绝保存。校验通过后笔记写入数据库，如果作者有关注者，还会把这条笔记推送到每个粉丝的收件箱中。

点赞功能用 Redis 有序集合记录，以用户点赞的时间戳作为分数。用户再次点击会取消点赞，点赞记录随之移除。笔记详情页展示最早点赞的用户头像，直接取集合中分数最小的前几名。点赞数据同时用于热门榜单的排序。

笔记列表采用滚动分页，避免传统分页在数据频繁变化时出现重复或遗漏。查询时以最后一条记录的时间戳作为下一页的起点，每次向后取固定数量的结果。用户自己的笔记、某个作者的公开笔记都通过同样的方式分页加载。

### 关注关系

用户可以关注或取关其他用户。关注关系保存在数据库中，同时在查询"是否已关注"等场景结合缓存使用。平台支持查看共同关注：把当前用户和目标用户的关注集合取交集，得到双方都关注的人。

关注之后会产生信息流。平台采用写扩散的推模式：作者发布笔记时，把笔记 ID 连同时间戳写入每个粉丝的 Feed 集合。粉丝刷首页时，直接从自己的 Feed 集合中按时间倒序滚动取出笔记 ID，再批量查询笔记内容。这种方式让粉丝的读取非常轻量，代价是发布时要写入多个收件箱，适合以读为主的社区场景。

### 优惠券与秒杀

平台支持两类优惠券：普通优惠券和秒杀优惠券。商家发布秒杀券时，券信息写入数据库，同时把库存预热到 Redis。

秒杀是整个平台并发要求最高的环节，完整流程分为三个阶段。

第一阶段是资格校验，全部在 Redis 中通过一段 Lua 脚本原子完成。脚本依次判断库存键是否存在、库存是否充足、当前用户是否已经下过单。三项都通过后，脚本扣减库存并把用户记入该券的已下单集合。因为整个判断和扣减在同一个脚本中一次执行，所以不会出现超卖，也不会出现同一用户重复下单。校验不通过时脚本返回不同的状态码，服务端据此返回库存不足或不能重复下单。

第二阶段是异步下单。Lua 校验通过后，服务端先用 Redis 号段模式生成一个全局唯一订单号，立即把订单号返回给用户，真正的落库操作通过 RabbitMQ 异步完成。订单消息发送到交换机 X，经路由键 XA 进入正常队列 QA，由专门的消费者监听处理。

第三阶段是消费落库。消费者收到消息后，先获取 Redisson 分布式锁，再在事务中完成最终的一人一单校验、库存扣减和订单保存。库存扣减使用乐观条件，只在数据库库存大于零时才执行更新，作为 Redis 校验之外的最后一道防线。消息处理成功后手动确认，处理异常时拒绝并重新入队。队列 QA 设置了消息有效期，长时间未被成功处理的消息会转入死信交换机 Y 和死信队列 QD，由另一组消费者做兜底消费，保证每一条订单最终都会被处理。

秒杀之外的普通优惠券提供领取功能，并可以按店铺查询可用券列表。

### 图片上传

发布笔记时需要上传图片。上传接口接收文件后保存到服务器本地指定目录，目录位于前端静态资源下，保存成功后返回可访问的图片路径。删除笔记时对应图片也可以通过删除接口清理。上传目录的绝对路径在系统常量类中配置，部署时需要改成当前机器上的真实路径。

## AI 能力设计

平台落地了三个 AI 场景，它们都不是让模型独立完成全部工作，而是与数据库、Redis、业务规则协同。

### AI 店铺口碑总结

店铺详情页展示的口碑总结来自该店铺下的全部探店笔记。考虑到笔记数量可能很多，直接全量送给模型会带来上下文长度、延迟和成本问题，系统采用先分段、再聚合的两段式方案。

第一段是分段摘要。系统把一家店铺的笔记按固定组大小分成多组，每组单独请求模型，提炼出这一组的总结、高频亮点、独有特色和关键词。第二段是聚合摘要。所有分段摘要收集齐后，再请求一次模型，把它们聚合成一份完整的口碑总结，包含总体评价、消费建议、高频亮点和独有特色。

缓存分三层设计。分段摘要单独缓存，同一家店的分组可以复用；最终总结也单独缓存；每份缓存还配合一个内容指纹，指纹由笔记 ID 与更新时间计算，只要该店铺的笔记集合发生变化，指纹就改变，旧总结自动判定失效并重新生成。总结重建时使用分布式锁，避免并发请求重复触发模型。模型不可用或返回格式异常时，系统回退到本地规则生成的精简版总结。

对应的对外接口是按店铺 ID 查询总结，以及主动预热总结两个接口。

### AI 探店助手

探店助手解决的是"自然语言转推荐结果"的问题，而不是闲聊。用户输入自己的真实需求，比如想吃清淡的、想找能坐下喝茶的地方、想买瓶水顺便休息，系统结合用户当前坐标和当前查看的店铺类型给出推荐。

完整链路包含五步。第一步意图解析，模型从用户输入中提取意图摘要、店铺类型关键词、需要包含的关键词和需要排除的关键词，用户明确表达忌口或不要的内容会进入排除集合。第二步候选召回，优先使用 Redis GEO 在用户坐标五公里范围内按类型检索店铺，Redis 数据缺失时查数据库兜底。第三步规则粗排，根据评分、销量、距离等本地规则对候选店铺做初步排序并限制候选数量。第四步模型重排，把候选店铺连同店铺简介、服务信息、用户的包含与排除关键词一起交给模型，由模型综合判断后给出最终排序和每家店的匹配分数。第五步理由生成，模型为每家入选店铺生成一句个性化推荐理由。

其中店铺简介是专门为这一能力设计的数据字段。仅凭店铺名称、类型、评分无法回答口味偏清淡、能不能喝茶休息、方不方便停车这类问题，店铺简介字段承载了这些模型可以理解的经营信息。推荐结果还会做短期缓存，相同需求短时间内重复请求时直接复用。模型不可用时，整条链路退化为纯规则推荐，功能仍然可用。

### AI 笔记质检与风控

风控用于在笔记发布前识别风险内容，识别范围包括广告引流、联系方式泄露、隐私信息泄露、违禁违法内容、人身攻击和夸大营销。

风控采用前后端双重校验。用户在编辑页面点击发布时，前端先调用一次风控接口，把检测结果即时反馈给用户，体验更好；但前端不是安全边界，攻击者可以绕过页面直接调用接口，因此后端在真正保存笔记之前还会再强制校验一次，只有通过后才允许落库。模型返回的结果包含是否放行、风险等级、风险分数、命中的风险标签、具体原因和修改建议。模型不可用时，服务端使用内置的关键词规则兜底，高风险类型同样会被拦截。

### AI 服务的六个内部接口

AI 服务对主业务服务提供六个内部接口：分段摘要、聚合摘要、意图解析、推荐理由生成、推荐重排、笔记风控。请求和响应都使用固定的 JSON 结构，并带有参数校验，保证主业务服务拿到的结果格式稳定。

## 缓存与可靠性

平台在大量场景使用 Redis，按用途可以分为几类。

会话类：短信验证码、登录令牌，均带有效期。业务缓存类：店铺详情、店铺分类、店铺类型相关数据。检索类：按店铺类型组织的 GEO 集合，支撑附近店铺检索。计数与关系类：笔记点赞集合、用户签到位图、关注 Feed 集合。AI 类：分段摘要缓存、最终总结缓存、推荐结果缓存、风控结果缓存，以及 AI 总结重建时使用的分布式锁。

针对缓存的三类典型问题都有对应处理。缓存穿透用空值缓存解决，查询不存在的店铺时缓存一个短有效期的空对象。缓存击穿用互斥锁解决，热点 Key 过期后只允许一个请求回源。缓存雪崩通过有效期配置和分层缓存降低影响。

系统层面的可靠性由两条机制保证。一是兜底，所有 AI 能力都同时具备模型实现和本地规则实现，任何一侧模型不可用都会自动降级，主业务服务本身也准备了规则版结果。二是异步可靠，秒杀订单通过消息队列异步落库，消费者手动确认消息，失败重新入队，长期未处理的消息进入死信队列由专门消费者兜底。

## 数据库结构

数据库名为 hmdp，核心表包括用户表和用户详情表、店铺表和店铺类型表、笔记表和笔记评论表、关注关系表、优惠券表和秒杀优惠券表、优惠券订单表。

店铺表除名称、类型、封面、地址、经纬度、评分、销量、评论数、营业时间等字段外，还包含店铺简介字段，用于保存给模型使用的经营信息。秒杀优惠券表在普通优惠券之外补充了库存、开始时间和结束时间。订单表记录用户、优惠券以及全局唯一订单号。

初始化脚本会创建完整表结构并导入基础数据，同时导入一批额外的美食类演示店铺和对应的探店笔记样本，这些样本预置了互动数据，专门用于展示口碑总结、探店助手和风控三项 AI 能力。

## 目录结构

- dianping-nginx-1.18.0：主业务服务，包含 Java 源码、资源文件、数据库脚本和内置的 Nginx
  - src/main/java/com/hmdp：controller、service、mapper、entity、config、interceptor、listener、tools、utils 等分层代码
  - src/main/resources：应用配置、MyBatis 映射文件、Lua 脚本、数据库脚本
  - nginx-1.18.0 dianping：Nginx 可执行文件、配置和前端静态资源目录
- hmdp-ai-service：独立 AI 服务，包含内部接口控制器、数据传输对象和编排服务
- sql：完整的数据库初始化脚本 open-source-full-init.sql
- docs：文档资源目录
- 项目理解文档.md：更完整的设计思路、实现细节与常见问题说明

## 本地运行

### 环境要求

需要准备：JDK 8（主业务服务）、JDK 17（AI 服务）、Maven 3.9 以上、MySQL 5.7 或 8、Redis 6 以上、RabbitMQ 3、Nginx 1.18（仓库中已附带 Windows 版本）。

### 第一步：初始化数据库

在 MySQL 中执行 sql 目录下的 open-source-full-init.sql。脚本会自动创建 hmdp 数据库、创建全部表结构、加入店铺简介字段、导入基础演示数据、导入额外的美食演示店铺，并为这些店铺生成探店笔记样本。

### 第二步：配置主业务服务

打开 dianping-nginx-1.18.0/src/main/resources/application.yaml，按本机实际情况确认数据库连接地址、用户名和密码，Redis 的地址、端口和密码，RabbitMQ 的地址和账号。配置文件中 hmdp.ai 开头的一组参数控制 AI 相关行为，包括 AI 服务地址、连接和读取超时、总结的笔记上限与分组大小、各类缓存有效期、探店助手的检索半径和候选数量等，默认值可以直接使用。

### 第三步：配置 AI 服务

AI 服务的模型配置全部从环境变量读取。在 Windows 下设置 DASHSCOPE_API_KEY 为自己的密钥，设置 DASHSCOPE_MODEL 指定使用的模型，例如 qwen-turbo-flash，还可以通过 DASHSCOPE_TEMPERATURE 调整生成温度。需要修改服务端口时设置 HMDP_AI_PORT，需要调整日志级别时设置 HMDP_AI_LOG_LEVEL。

### 第四步：配置图片上传目录

打开 SystemConstants.java，把图片上传目录常量改成本机前端静态资源中 imgs 目录的真实绝对路径，否则上传的图片会写入错误位置。

### 第五步：检查 Nginx 配置

Nginx 配置位于 nginx-1.18.0 dianping/conf/nginx.conf。默认监听 8080 端口，根路径指向静态资源目录，/api 请求转发到本机 8081 的主业务服务。前端请求基址统一为 /api，因此页面应始终通过 Nginx 访问，而不是直接打开静态文件。

### 启动顺序与命令

推荐按依赖顺序启动：先启动 MySQL、Redis、RabbitMQ，再启动 AI 服务，然后启动主业务服务，最后启动 Nginx。

两个后端服务都可以用 Maven 启动，分别进入 hmdp-ai-service 和 dianping-nginx-1.18.0 目录执行 mvn spring-boot:run。Nginx 在其目录下执行 start nginx.exe 启动。

启动完成后的地址：前端页面 http://127.0.0.1:8080 ，主业务服务 http://127.0.0.1:8081 ，AI 服务 http://127.0.0.1:8090 。

### Redis 预热

数据库脚本只负责 MySQL，Redis 中的数据默认在业务第一次访问时自动回填。如果希望提前把附近检索所需的 GEO 数据和店铺缓存准备好，可以在 IDE 中运行 DemoDataSeedRunner，它会完成数据预热和完整性校验。

## 接口一览

面向前端的主要接口按模块划分：用户模块提供发送验证码、登录、登出、当前用户信息、用户资料、签到和签到统计；店铺模块提供店铺详情、新增、修改、按类型分页查询和按名称搜索；店铺类型模块提供分类列表；笔记模块提供发布、点赞、笔记详情、点赞用户、热门榜单、我的笔记、用户笔记和关注流；评论模块提供笔记评论；关注模块提供关注与取关、是否关注、共同关注；优惠券模块提供发布、秒杀、按店铺查询；订单模块提供秒杀下单；上传模块提供图片上传与删除；AI 模块提供店铺口碑总结、总结预热、助手推荐和笔记风控。

AI 服务侧的接口统一位于 /internal/ai 路径下，包括分段摘要、聚合摘要、意图解析、推荐理由、推荐重排和笔记风控六个端点，仅供主业务服务内部调用。

## 代码阅读指南

建议按从外到内的顺序阅读。先看主业务服务的控制器层了解接口划分，再进入服务实现层看业务逻辑。与 AI 直接相关的入口是 AiController，核心编排在 AiServiceImpl，包括缓存判断、指纹生成、摘要组装和噪声清洗；调用 AI 服务的 HTTP 客户端位于 ai/client 目录；Redis 键定义集中在 RedisConstants；笔记发布时的风控拦截位于 BlogController。

秒杀链路从 VoucherOrderController 进入，VoucherOrderServiceImpl 包含 Lua 执行、订单号生成和消息发送，消费者位于 listener 目录，队列与交换机定义在 QueueConfig。

AI 服务从 InternalAiController 进入，所有提示词、模型调用和本地兜底逻辑集中在 AiOrchestrationService，数据传输对象位于 dto 目录。
